## What this is

Fractional ML engineering for fintech and data teams that have working models but unreliable production surfaces. The gap is not usually the model code. It is the surrounding infrastructure: unclear ownership, fragile inference boundaries, observability gaps, and technical decisions that cannot be defended under audit scrutiny.

This is scoped consulting — deliverable-led, not hourly. Each engagement ends with working infrastructure and documented decisions, not a report of recommendations.

## Engagement types

**Production ML pipeline review**

End-to-end audit of inference serving, retraining cadence, feature store design, and monitoring coverage. Output: a ranked list of correctness risks, an architecture decision record for each significant choice, and an implemented fix for the highest-severity items.

**Incident remediation**

Post-incident root cause work for ML systems — silent accuracy degradation, cache invalidation failures, feature distribution drift, OOM crashes under load. The deliverable is a working system, not a write-up of what happened.

**Inference optimisation**

Latency analysis for prediction serving under concurrent load. Common sources include a missing cache layer, synchronous feature fetches on the hot path, non-batched model calls, and cold-start latency on model load. The deliverable records the baseline, the chosen intervention, and the measured result for that system.

**Audit-traceable ML documentation**

For teams where model behaviour must be explainable and traceable. Covers model cards, decision rationale documents, and audit trail implementation. Built from the actual system rather than presented as regulator certification.

## What changes in practice

The first session maps the actual system against what the team believes the system to be. These are almost always different. The gap — between the mental model and the production behaviour — is where most production issues live.

Once the gap is mapped, the work is triage: which correctness risks are live now, which are latent, and which are acceptable given the operating constraints. From there, the engagements are sequential — highest severity first, documented decisions throughout.

## Operating principles

Every deliverable is traceable to a production system. No invented benchmarks, no template documents presented as bespoke analysis. If a recommendation cannot be justified against the specific system and its specific constraints, it does not go in the deliverable.

Completion criteria are agreed against the named system risk and evidence required for handoff.

## Relevant experience

The SabiScore and TaxBridge case studies show the working method: establish the failure boundary, record the decision, measure the outcome within a named window, and label private evidence as private. Client-system evidence remains subject to the engagement's disclosure boundary.
